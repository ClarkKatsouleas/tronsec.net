Multi-Network Architecture & Design Implementation

A comprehensive and logically-designed WAN environment architecture

Project Introduction

Initial planning for this project architecture began in February 2025, with physical implementation starting in March 2025. However, due to the scope of the project at the time, it was not completed within the given timeframe before needing to move on. Therefore, now a year later in 2026, I have come back to the project with the original configurations to complete it as originally intended.

This lab environment was originally drafted as a way to practice eBGP and iBGP within an enterprise setting, to analyze their functions. Virtual Routing and Forwarding was later added in the design phase as the network took distinct shapes with the three mini-topologies that became the RED, BLUE, and GREEN VRFs and autonomous systems. I knew I wanted a single routing domain to exist in all routers for general management and SSH connectivity, and while I could have used the global routing table. I thought it would be more fun to additionally incorporate a new VRF, hence the 4th VRF in the architecture, MGMT. The lab incorporated enterprise-grade hardware including Cisco Catalyst 3750e switches (x5), Cisco 2901 routers (x6), Cisco ISR 4331 routers (x3), Cisco 2911 routers (x2), and a Cisco Nexus 5548UP (x1). Network Architecture & Topology Design

This network was set up to allow for logically separate routing domains by use of different customers of MGMT: RED, BLUE, and GREEN. External Border Gateway Protocol was used with public IP addresses to peer with each customer in-turn, and route traffic appropriately between them and the internet access gateway. iBGP was used for MGMT's VRF to provide scalability of routing tables through a single autonomous system. Each customer was established to be using a different internal routing protocol within their internal LANs for a wide berth of architectural and design challenges. Additionally, a VPN was established between sides of the network as an overlay to securely route traffic across NAT boundaries. To support the growing ISP's systems and infrastructure, four primary Virtual Routing and Forwarding (VRF) instances were established throughout the network: RED, BLUE, GREEN, and MGMT each given a corresponding vlan tag to carry their traffic: 11, 22, 33, and 99.

VRF RED (VLAN 11)

  • Subnets: 10.0.10.0/24, 10.0.11.0/24
  • Traffic Designation: Red
  • Routing Protocol: Intermediate System-to-Intermediate System (IS-IS)
  • VRRP for First-Hop Redundancy Protocol with interface tracking

VRF BLUE (VLAN 22)

  • Subnets: 172.16.10.0/24, 172.16.20.0/24, 172.16.22.0/24
  • Traffic Designation: Blue
  • Routing Protocol: Open Shortest Path First
  • iBGP peering scalability with route-reflectors within AS 65200

VRF GREEN (VLAN 33)

  • Subnet: 192.168.30.0/24, 192.168.33.0/24
  • Traffic Designation: Green
  • Routing Protocol: Enhanced Interior Gateway Routing Protocol (EIGRP)
  • Named mode connectivty for use with VRFs
  • Hot Standby Router Protocol in-use with priority for MGMT VPN reachability

VRF MGMT (VLAN 99)

  • Subnet: 10.26.10.0/24, 10.0.99.0/24, 172.16.99.0/24, 192.168.99.0/24
  • Traffic Designation: Yellow
  • Routing Protocol: BGP
  • VPN between AS 65200 and 65300 to allow for cross-system communication
  • In-use by all routers for management reachability and SSH connectivity

Physical Infrastructure

  • EH-WICs and NIM modules for network expandability
  • Copper SFPs and Switch Stack Module for network medium conversion and scalability
  • Green Async Cable Connections to the console port on all devices
  • RJ-45 CAT6 UTP Cables for general connectivity
  • MM Fiber Connections for core-to-distriution switching connectivity

Physical implementation of the network infrastructure

Network Connectivity & Routing

Below are in-depth looks at each site and routing domain within this lab. They are listed in hierarchical order of Autonomous System Number.

VRF RED

The network architecture for VRF RED was established within autonomous system 65100. It illustrates an IS-IS network with type 1 and 2 and type 2 routers for network connectivity to client workstation PC2. Central router T-ISR-C acts as a DHCP server for the networks within this site. T-ISR-B and T-2901-C act as redundant default gateways with VRRP where T-ISR-B matches the virtual IP address as the master router. As the master router is hard-set, an IP SLA is set up with interface tracking to T-ISR-B's WAN interface in VRF RED. If that interface goes down, VRRP is set to failover to T-2901-C as the new default gateway for the subnet.

VRF BLUE

Next, ASN 65200 was used for VRF BLUE. This autonomous system showcases use of OSPF with a multi-area design. The backbone area 0 was used to connect all internal router-to-router connections, while areas 1 and 2 connected to client workstation PC1 and servers ESXi, NS1, and NS2. T-3750-A and T-3570-B were connected with stackwise cables to allow for more client connections and ease of management without sacrificing physical ports.

VRF GREEN

Additionally, VRF GREEN used AS 65300. This autonomous system used EIGRP in named mode for use with VRF address families. It operated Hot Standby Routing Protocol on routers T-2911-B and T-2901-A. T-2901-A was influenced with priority to become the default gateway and preempt over the backup router. Because T-2901-A was a VPN concentrator for VRF MGMT within the AS, traffic would have been dropped due to split-horizon if the other router was the gateway.

VRF MGMT

Finally, the MGMT VRF was used across all VRFs and all autonomous systems. It was used to translate all traffic from the different VRFs to itself at the external interface at the gateway for general internet access. This was accomplished through the use of specific route-maps and network address translation VRF statements. Additionally, most VRFs had specific route-maps at their provider edge routers. These were used to filter specific NAT statements to allow for load balancing NAT across multiple interfaces for each VRF. iBGP was specifically used within AS 65200 for the MGMT VRF to allow for greater filtering of external dynamic routing when using two paths into the AS. This allowed for further granular filtering of routes in and out of the AS within the VRF. A site-to-site VPN was established between the autonomous systems 65200 and 65300 within the MGMT VRF. This allowed for remote authentication devices within AS 65300 to use authentication and DNS resource servers located within AS 65200. The MGMT VRF was established as both the transit or front door VRF, and the VRF sending and receiving the encapsulated traffic.

Services & Authentication

RADIUS & Active Directory

Remote Access Dial-In User Service (RADIUS) domain-based authentication was established on most networked devices. The only devices it was not established on were internal devices within AS 65100 as they would not have had reachability from behind NAT on T-2901-D. In the future, a VPN could be established pointing between AS 65100 and 65200 to allow for extended server connectivity outside of VRF RED's ASN. For now because of time requirements, it was out of scope of the lab architecture.

DNS

DNS was established on a pair of Alma Linux machines, NS1 and NS2. The servers were dished out based on resource availability. One server (NS1), was provisioned for VRF BLUE, while the other was provisioned to VRF MGMT with respective DHCP IPs.

DHCP

Finally, DHCP servers were established using Cisco routers for IPv4 client connectivity. Some subnets required dhcp relay connections to reach their respective server in their given site. Only one issue was encountered here, where it was required that the proper VRF be specified for some of the pools, which were refusing to take clients otherwise. However, once this was ironed-out, all pools worked without issue and connectivity could be tested across the environment and to the internet.
